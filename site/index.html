What this proves

Five problems that only show up when you build the whole thing

Each of these was found in this codebase, reproduced, and fixed with a test that failed first. The file is named so the claim can be checked rather than believed.

Concurrency

A race that only exists above one worker. Choosing an explanation provider per request was done by writing to a module-level singleton and restoring it afterwards — and the restore was not in a finally. Two concurrent requests saw each other's settings, and any request that raised in between left the singleton altered for every request after it.

The fix was not a lock. The provider is now injected once at construction and never reassigned, so there is no mutable state for a second request to disturb: the race is structurally impossible rather than defended against.

src/agents/explaining/__init__.py · docs/adr/002-llm-provider-abstraction.md

Determinism

The same input scored two different numbers. Keyword extraction took [:20] from a Python set. String hashing is randomised per process, so set order changed between runs — the same CV against the same job scored 0.40 or 0.45 depending on which process answered. Measured across five processes.

Terms are now ranked by frequency and tied alphabetically, which is both deterministic and more useful: a term repeated in a job description matters more than one that appears once.

src/agents/agent3_scorer.py · tests/unit/test_skill_normalization.py

Idempotency

Seeding that cannot overwrite your data. The job corpus began as a read-only JSON file and became writable through POST /jobs. On a host with an ephemeral filesystem the obvious implementation reseeds on every deploy and silently discards every edit anyone made.

seed_jobs returns zero and writes nothing if the table is already populated, so a redeploy is a no-op and the JSON file is a seed rather than a source of truth.

src/storage/database.py

Trust boundary

Rate limits charged to the right client. Per-IP limits read the socket address, which behind a proxy is the proxy's — so every visitor shares one bucket, ordinary traffic starts collecting 429s, and an attacker is no more limited than before.

X-Forwarded-For fixes it and is client-supplied, so it is only believed when TRUST_PROXY_HEADERS says something is in front. It defaults to off, because the opposite mistake is worse: trusting that header with nothing in front lets any client invent a fresh identity per request.

Honest metrics

Target leakage found in my own model. It scored a perfect 1.000 ROC-AUC. Removing the feature I suspected changed nothing — the metrics came back identical to the digit. Digging further: the label is a threshold on a column already excluded from training, and two ordinary columns rebuild it anyway. Experience alone reaches 0.9244; with Projects Count, 0.9933.

No feature engineering makes that dataset non-trivial, so the finding is reported instead of the score. GET /stats publishes no accuracy figure at all, and a contract test asserts none ever appears.

models/production/model_metadata.json · tests/integration/test_api_contract.py

Silent failure

A degraded run must not look like a healthy one. A rule-based explanation and a model-written one are both fluent paragraphs. With a provider configured but unreachable — dead key, spent quota, no network — a broken demo is indistinguishable from a working one.

Every match carries explanation_source and the interface prints it; scoring_mode says whether the ML model ran; and /health names the provider that will actually answer rather than reporting a config flag.

How a score is built

Five weighted components, each returned separately

ComponentWeightWhat it measures
Skill match50%CV skills against required and preferred, both resolved to the vocabulary
Experience20%Years against the stated range, penalising both directions
Title similarity17%The candidate's role against the job title
Education8%Highest degree against the stated requirement
Keyword overlap5%Terms from the description present in the CV

Enforced, not documented. The weights live in config/agents.yaml and nowhere else. A set that does not sum to 1.0 fails at import with the offending values named, and a contract test asserts the five components add up to the reported rule-based total — because a stacked bar built on drifting weights does not look wrong, it looks right.
